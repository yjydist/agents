description: |-
  Create and revise GitHub goal issues and verifiable sub-issues, keeping scope, dependencies, progress, and goal closure aligned with evidence.
  Use when:
  - A user wants to turn a broad direction into a tracked goal and actionable sub-issues.
  - A goal spans sessions, or a tracked task has multiple independent outcomes and needs smaller executable boundaries.
  - New evidence or a changed direction requires revising, splitting, cancelling, or replacing goals, tasks, or dependencies.
  - Goal progress conflicts with actual results, the next step is unclear, or the goal may be ready to close.
  Not for:
  - Executing or handing off a bounded issue without a planning problem, choosing code refactoring boundaries, or organizing commits from existing changes.

# 目标与路线管理

用 GitHub 父 issue 保存 goal, 用 sub-issue 表达可接手和验收的 mini todo. 目标可以从宽泛想法开始, 路线随证据和反馈调整. 本技能交付目标, 任务边界, 依赖及可信的进展记录; 仅请求规划时不实施产品变更, 已授权实施时规划后继续完成相应工作, 不因阶段切换新增审批.

## 读取现状与确定完成含义

- 从当前请求, 仓库和指定 issue 确定目标及 GitHub 仓库. 检查已有目标, 子任务, 相关评论和实现证据, 复用已有记录, 不为已有工作再建平行目标. 读取列表时处理分页, 避免将未读到的任务当作不存在.
- 明确要解决的问题, 当前成功条件, 范围边界与关键未知项. 能从项目查明的事实自行调查; 影响目标含义的缺失选择向用户澄清. 无法确定的方向留为未知或调查任务, 不编造需求补齐路线.
- 明确完成条件落在何处, 如本地验证, 合并或上线. 沿用项目和已有任务约定, 子任务可以有不同的明确完成条件. 约定不明且影响关闭判断时先澄清, 不默认代码写完就算交付.
- 使用环境支持的已认证 GitHub CLI 或 API 连接器, 核对实际可用的读写能力. 用户已授权管理目标和任务时直接完成相关创建, 更新和关闭; 仅请求讨论或草稿时交付可审阅文本. 权限或工具不足时说明未同步项, 不悄悄换成本地台账或声称远程操作成功.

## 保存目标与拆分近期工作

父 issue 正文保持为当前目标的简明入口, 至少包含:

| 内容 | 记录要求 |
| --- | --- |
| 目标与原因 | 解决的问题, 达成后的结果与价值 |
| 成功条件 | 可核对的整体验收条件及完成所处阶段 |
| 范围与约束 | 当前包含和排除的工作, 必须保留的行为 |
| 当前进展 | 已验证结果和关键决定的一行摘要, 链接其详细证据 |
| 尚未细化 | 属于目标但还不能准确描述的方向或未知项 |
| 下一步 | 推荐可执行任务的标题与链接, 选择理由或当前阻塞 |

任务归属和状态由原生 sub-issue 关系承载, 父正文不再手工复制一份完整状态清单. 默认目标与任务两层, 只有一个方向本身确实跨越多个可验收任务时才增加中间层. 中间层也有明确成功条件, 叶子任务才是通常的执行单元.

- 一项任务交付一段完整可验证行为, 或回答一个能解除不确定性的具体问题. 不按数据库, API, UI 等技术层机械拆分. 必须分批迁移时设计可验证的中间状态, 明确兼容路径和最后的整体验证.
- 单个 session 的规模包含理解, 实施或调查, 验证与状态回写. 无法在有限上下文中接手, 包含多个独立结果或缺少可验证终点时重新划分; 不用固定 token 数, 文件数或工时保证完成.
- 只创建当前能准确描述的问题或结果. 问题明确但依赖尚未完成时可以先建阻塞任务; 连问题都依赖前置答案时留在尚未细化, 不提前铺满猜测性的任务.
- 每项任务写清: 父目标及本项贡献, 交付结果, 本项范围和不包含的工作, 验收条件与验证方式, 所需前置结果, 后续任务依赖的输出或契约, 必要代码与证据入口. 未知的后续工作不强行建票, 可链接父目标中的相关方向.
- 子任务内的普通编辑步骤用 checklist 即可. 为独立交付, 调查, 接手或阻塞关系创建 issue, 不把每次工具操作拆成任务.
- 用原生父子关系表达归属, 用原生 blocking 关系表达执行前提, 不以正文链接冒充已建立关系. 只记录真正阻止开始的依赖, 区分建议顺序与必要前提, 检查循环依赖并修正边界或前提.
- 优先选择能验证关键假设或交付最小完整行为的可执行任务. 可执行意味着所需前提实际成立且未被其他 session 占用, 不能仅凭前置 issue 已关闭判断, 也不把 assignee 当作可靠的 session 锁.

## 调整目标与任务

用户已明确改变方向时按新要求处理; agent 发现原方向可能不合适时提供证据与建议, 不自行替换目标. 局部可逆的路径调整在原授权内推进, 只有尚未解决的目标或契约选择需要用户决策.

| 变化 | 调整方式 |
| --- | --- |
| 路径变化, 目标不变 | 修改相关任务的范围, 验收与依赖, 更新下一步 |
| 目标范围或成功条件变化 | 记录变更原因及新旧差异, 更新父正文, 沿受影响依赖核对子任务和已完成结果 |
| 原目标被放弃或替代 | 保留原目标记录并以 `not planned` 关闭, 说明原因, 链接替代目标并处理原任务去向 |

- 对受影响任务分别判断保留, 修改, 新增, 拆分或取消. 拆分后仍要汇总验收时原 issue 保留为父任务; 被新任务完全替代时以 `not planned` 关闭并链接承接任务, 不标为成功完成. 不删除旧 issue 抹去历史.
- 已完成任务保留当时的验收依据. 新需求产生新工作时建立后续任务; 原验收误判或原契约并未满足时重新打开并说明证据. 不能为适应新目标改写历史结果.
- 核对被取消或改变的前置结果是否仍被后续任务需要, 以及依赖是否需要移除, 替换或重新阻塞. 更新所有受影响的后续关系, 不把取消视为前提自动成立.
- 对进行中的任务注明已有分支, PR 和成果的保留, 复用或待处理方式, 更新接续点并协调执行者. 目标调整本身不授权丢弃工作区修改, 回滚代码或关闭 PR.
- 在变更评论保留原因和证据, 父正文更新为当前方向并链接该评论. 已细化的未知项迁到新任务后从尚未细化中移除, 避免同一工作在两处长期维护.

## 核对事实并同步收尾

- 接续目标, 调整路线或核对进度时, 对照相关代码, PR, 实际检查和验收条件读取当前状态. 同一次变更可能满足多个任务, 逐项核实并及时补记, 不依赖先前 agent 的完成声明. 只调查本目标及受影响范围.
- 满足任务完成条件时记录结果与证据, 勾选真实通过的验收项, 以 `completed` 关闭. 待合并, 待上线, 验证不足或被阻塞时保持打开并明确等待事项. 取消和替代使用 `not planned`, 不计入成功交付.
- 从叶子任务向上检查中间目标与最终 goal. 核对当前整体验收和未细化事项, 不能仅凭子任务全部关闭或进度百分比判断成功. 目标已达到时处理剩余冗余或失效任务, 给出整体验收证据并及时以 `completed` 关闭; 原验收误判时重新打开.
- 写入前重读受影响记录, 保留并发更新, 避免用旧正文覆盖他人修改. 创建后记录返回的 URL, 再建立关系; 响应不确定时先读取确认, 避免重复建票. 部分成功时列出已完成操作和待同步差异, 从缺失步骤恢复. 重读只能减少冲突, 不提供原子锁.
- 写入后回读核对正文, 父子关系, 依赖及关闭原因. 交付目标和下一项任务的标题链接, 实际同步结果及剩余阻塞. 外部合并或上线尚未发生时明确下一次核对入口, 不声称技能会在 session 结束后自动监听.
