  Use when:
  - A user requests refactoring or code simplification with a concrete structural problem or target.
  - The current task needs a scoped change to tangled responsibilities, duplicated state, scattered rules, or file organization.
  - Understood wrappers, obsolete paths, configuration combinations, or repeated concepts need to be consolidated or removed while retaining their required behavior.
  Not for:
  - Assessment-only requests, choosing where to refactor without evidence, test-suite maintenance alone, or routine feature work without structural problems.

# 通用重构

围绕用户指定的问题与范围, 用可验证的小步变更改善代码结构, 文件组织与目录结构, 降低现有系统的理解与修改成本. 默认保持可观察行为和兼容契约, 包括失败语义与对外副作用. 功能裁减或契约变化须有明确需求依据, 不能从重构请求中自行推导.

用户请求实施时, 在已授权范围内完成实际修改和验证; 仅请求分析或计划时, 提供对应产出. 根据目标项目的约定调整工作方式, 不把局部重构扩大成无关的全库整理.

## 核对本轮依据

从相关实现, 调用方, 测试和工作区状态核对具体维护问题, 目标边界, 必须保留的行为与验证方式. 这些依据可以在当前任务中直接建立, 不要求独立分析文档或配套技能. 已有分析只复核会影响本轮决定的证据, 不重复全量探索.

问题或目标尚不清楚, 或新证据使边界选择失效时, 先集中调查该疑点, 不边大范围试改边寻找理由. 修改前简要说明问题证据, 保留行为, 删改范围, 目标结构和验证方式; 局部可逆选择自主判断, 无法查明且影响需求或外部契约的歧义再澄清.

## 选择重构动作

按已识别的问题选择动作, 不把下面各项当作清理清单. 结合实际调用和约束判断候选结构的收益; 收益不足时保留现状并说明依据.

- 删除或内联一层前, 推演其规则与协调逻辑将去往何处: 无必要的转交是否消失, 相关复杂度是否集中, 还是仅转移或重复到调用方. 据此判断它是否隐藏了必要决策或维护了契约; 不因只有一个调用方或一种实现就认定它无用.
- 合并共同语义和变化原因一致的重复表达. 若合并后需要不断增加开关, 特例或跨模块同步修改, 重新检查是否混合了不同概念. 允许暂时重复, 不按表面相似度强行复用.
- 按职责和易变决策调整边界, 集中相关规则, 状态归属与副作用, 让接口提供调用方需要的完整能力. 评价接口复杂度时, 计入调用方必须掌握的前提, 调用顺序, 配置和失败处理, 不只统计方法与参数. 拆分或抽象应减少这些知识或修改的传播范围, 不把内部步骤与中间状态推给调用方, 不合并无关职责或为假想需求预建扩展点.
- 按职责, 共同变化原因和依赖边界组织文件与目录, 将紧密相关的实现放在一起. 本轮范围内有明确维护收益时, 主动重命名, 移动, 拆分或合并, 让人和 Agent 能从命名与层级定位入口, 理解职责并找到相关上下文. 遵循项目惯例, 不套用固定目录模板, 不为形式统一增加层级或过度拆分.
- 收敛重复状态, 无必要的配置组合和并行路径. 能从明确来源可靠推导的信息优先计算, 必须保留副本时检查同步与失效规则. 简化回退和错误处理时保留必要的恢复行为, 不用默认值或吞错隐藏失败.
- 删除候选内容前检查实际调用, 导出, 注册和配置加载途径及兼容要求. 搜索不到直接引用只是线索, 不能据此删除公开接口或动态入口. 用途不明时先查证, 证据不足则收窄当前删改范围并说明限制.

## 小步实施与验证

- 按可独立验证的行为或职责小步调整结构, 同步更新受影响的调用方, 每步复用能发现相关回归的现有检查. 根据风险和反馈决定下一步, 局部实现选择自行判断.
- 调整文件或目录路径前, 检查受影响的导入导出, 动态发现与加载, 资源定位以及构建和测试配置. 调用方依赖的公开路径按兼容契约处理. 同步更新受影响的引用和配置, 将路径调整及其配套更新作为完整变更, 按实际影响验证加载, 调用及构建行为.
- 局部测试充分但流程仍易错时, 检查调用顺序, 数据传递和失败处理是否散落在调用方, 明确协调职责, 并通过承担完整职责的接口验证组合行为. 跨模块调整时补齐必要的调用方与集成验证, 完成项目要求的检查; 扩大或重复检查应有新的变更, 失败或未解决风险作为依据.
- 测试预期依据明确需求, 外部契约, 已确认实例或领域不变量, 不能仅从待验证实现反推. 检查实际结果及必要副作用, 覆盖相关边界和失败情况. 内部结构变化不应迫使业务预期随之改变.
- 替换绑定私有函数或中间结构的测试时, 先在原实现上运行新的行为测试, 确认测试通过且其断言保留了需要保护的业务事实, 再调整实现并移除被替代的测试.
- 被测文件移动或实现替换不意味着所保护的行为失效. 删除测试前核对必要断言由哪些验证承接, 不因测试到期, 失败或覆盖率情况而删除, 不根据新实现整体重建测试.
- 测试不足时, 先用最小的相关验证固定关键行为, 再修改有风险的路径. 区分实际行为与需求规定, 不把发现的缺陷固化为正确预期; 是否修复按任务范围处理, 不混入未约定的行为变化. 不为测试数量, 覆盖率或本次重构搭建通用测试框架.
- 检查失败时区分已有问题和本次回归, 不通过跳过检查, 削弱断言或无依据地更新预期换取通过. 无法运行必要检查时说明原因和验证边界, 不把静态阅读或局部检查表述为完整验证.
- 替代实现得到验证后, 清理失去用途的旧代码, 配置, 依赖和接口, 同步修正受影响的说明. 必须暂时保留的过渡路径应有明确退出条件, 避免过渡实现长期残留.

## 审查与交付

审阅实际差异, 确认必要流程和契约仍然成立, 没有遗漏调用方或引入不必要的状态, 文件与目录表达的职责边界与实际依赖一致. 对照预期收益, 用具体维护场景的前后变化判断入口与相关实现是否更易定位, 所需上下文是否更集中, 修改是否需要知道更少细节, 改动更少位置或验证更少状态组合. 不以目录外观整齐, 文件数或代码行数下降代替这个判断.

交付时分别简要说明结构调整及其维护收益, 实际完成的验证和剩余限制. 工作目录和交付物按任务要求选择. 目标达到且验证充分后结束, 不为继续优化扩大范围.
